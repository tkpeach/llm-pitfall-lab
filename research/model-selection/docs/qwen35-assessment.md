# Qwen3.5 作为项目目标的可行性评估

> 前期调研归档：本文件包含历史候选和讨论中间状态，不是正式执行规格。当前路线见 [模型路线](../../../docs/model-plan.md)，资源要求见 [资源规则](../../../docs/resource-policy.md)。

日期：2026-10-22。对象：当前 Apple M4、24 GiB 统一内存、macOS 15.7.3；已安装 MLX 0.32.4 / MLX LM 0.32.2。模型路线现已确认：一期 4B 完整学习，二期 9B 迁移。以下评估保留选型时证据，完整运行尚未验证；资源数值仍待确认，见 [资源使用规则](../../../docs/resource-policy.md)。

## 1. 结论与证据边界

Qwen3.5 值得优先验证，但当前不能承诺 9B 能在本机完成一期所有训练实验。

| 目标 | 4B | 9B |
| --- | --- | --- |
| 短上下文量化文本推理 | 高优先级可行候选 | 资源预算支持优先验证，尚未实测 |
| BF16 文本推理与数值对照 | 比较有余量，仍需测加载峰值 | 权重已占据大部分资源，不作为默认路径 |
| 短序列 LoRA / 量化 LoRA | 有条件可行候选，先验证检查点和层选择 | 有条件候选，内存与时间约束更强 |
| 在线强化学习受控实验 | 必须提前验证，不能由 SFT 推断 | 高风险，不作为升级时的默认承诺 |
| 全参数训练 | 不作为主模型路径 | 不纳入当前资源承诺 |
| 长上下文、大批量、多方法同时运行 | 按明确问题单独预算 | 不作为日常实验默认配置 |

“可行候选”来自结构、文件预算与核心算子测试，不等于预训练模型实测。尚未下载 Qwen 权重，也未测生成速度、完整训练峰值、训练效果或小时级运行成本。

本轮完成三类工作：核对官方配置及明确 revision；检查已安装源代码；在 M4 GPU 上测试真实头数与头维度的单个递推核心算子。未改变底层库或运行系统设置。

## 2. 文本范围与机制学习

Qwen3.5 原始模型带视觉编码器。若采用它，需明确范围为“仅运行、训练和观察语言部分，排除视觉流程”，而非声称原始底座是纯文本。用户已确认选用本系列开展文本项目，执行范围据此限定为语言部分；不增加视觉学习或运行目标。

已安装的 `qwen3_5.Model` 构造 `language_model`，权重整理排除视觉键；这为文本执行提供具体实现依据。仍需验证下载/加载峰值、tokenizer、对话模板及裁剪后的权重来源，避免仅根据 Hub 标签或仓库名判断。

4B 和 9B 都是稠密 FFN 模型，不因采用混合注意力而成为 MoE。二期的 MoE 后训练安排不因此提前。

两者均有 32 层：24 个 Gated DeltaNet 层和 8 个 full attention 层。因此学习应分开观测：

- Full attention 的 Q/K/V、位置、mask 与 KV cache。
- Gated DeltaNet 的卷积历史、递推状态和更新过程。
- 两种层的执行开销、数值与资源差别。

这增加了前沿机制的学习价值，也增加了从零学习的负担。需要通过最小实验逐步建立概念，不能把所有层都解释为常规 KV cache。标准 Attention 的完整机制可以在真实 full attention 层和最小机制实验中学习，不必另维护一个主模型。

依据：[4B 配置](https://huggingface.co/Qwen/Qwen3.5-4B/blob/main/config.json)、[9B 配置](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/config.json)、[MLX 实现](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/qwen3_5.py)。本地配置快照见 [qwen35-candidates.json](../evidence/qwen35-candidates.json)。

## 3. 内存：权重、缓存与训练必须分别计算

GB 为十进制，MiB/GiB 为二进制。系统实测总内存 24 GiB，MLX 推荐 GPU 工作集约 16 GiB；后者不是硬上限，也不是当前空闲预算，仍需给系统与其他应用留余量。

### 权重和下载包

| 数据量 | 4B | 9B |
| --- | --- | --- |
| 按名义语言参数量估算，仅 BF16 权重 | 约 8 GB | 约 18 GB |
| 同条件，理想 4-bit 数据 | 约 2 GB | 约 4.5 GB |
| 官方完整 checkpoint 元数据参数量（含非文本组件） | 约 46.60 亿 | 约 96.53 亿 |
| 查询的 MLX 4-bit 包 safetensors 总文件大小 | 约 3.03 GB | 约 5.95 GB |

名义语言规模并非精确参数统计；转换包文件大小包含其实际混合精度与组件安排，不是运行内存。尚未逐个检查包内 tensor 是否排除了视觉或 MTP，不以名称宣称它们一定是纯语言包。官方 checkpoint 和转换包是不同产物，必须分别固定 revision 与量化配置。

文件清单依据：[4B 转换包](https://huggingface.co/mlx-community/Qwen3.5-4B-4bit/tree/main)、[9B 转换包](https://huggingface.co/mlx-community/Qwen3.5-9B-4bit/tree/main)；查询快照见 [qwen35-quantized-file-sizes.json](../evidence/qwen35-quantized-file-sizes.json)。不下载大权重即可核对这些元数据。

判断：9B 量化推理值得验证；9B BF16 权重本身已接近/超出约 16 GiB 推荐工作集，不能认为统一内存 24 GiB 就能宽裕训练它。4-bit 权重也不能消除激活、logits、反向状态和临时副本。

### 推理状态

按本次官方配置，4B 与 9B 的 full attention 层数、KV heads 和 head dimension 相同。若 KV 为 16 bit、batch=1，两者理论数据量均为：

- 每 1024 个已缓存 token 约 32 MiB，4096 个约 128 MiB，8192 个约 256 MiB。
- 24 个线性层的 FP32 递推状态合计约 48 MiB；卷积历史还需另计。

这意味着从 4B 到 9B，推理缓存不必按参数量同比增大，但权重、投影、MLP 与输出层成本会增加。该结论仅适用于本次具体配置。缓存数据量不含分配余量，batch 按比例增加，长上下文依然会增加 Attention 计算和 KV 读取。

### 训练状态

最重要的预算风险来自递推反向过程和大词表输出，而不是缓存本身。

- 已安装实现中的 `GatedDeltaNet.__call__` 在训练模式调用可微 ops 路径，在推理模式使用专用 kernel；ops 路径按时间步递推。不能拿推理性能代表反向训练性能。
- `vocab_size=248320`；若完整 logits 为 FP32，batch=1、1024 token 的单个张量理论约 0.95 GiB。BF16 是其一半；loss、log-prob 等中间量还会增加开销，实际是否物化这些张量按实现确认。
- LoRA 减少可训练参数和优化器状态，不能自动消除经相关层反向传播的激活与递推状态。
- 首轮需比较短序列、逐层梯度检查点、低 rank、指定层与 microbatch=1；通过梯度累积扩大有效 batch。只训练尾部少量层可作为探测，但不能静默替代原本期望的训练覆盖。

## 4. 本机核心算子测试

复现脚本：[probe_qwen35_recurrence.py](../scripts/probe_qwen35_recurrence.py)。结果：[qwen35-recurrence-probe.json](../evidence/qwen35-recurrence-probe.json)。

输入采用与 4B/9B 相同的 16 个 QK heads、32 个 V heads、128 维、BF16；batch=1；FP32 递推状态。使用合成数据，测量单个核心算子的前向与对 Q/K/V/门控输入的反向，不含投影、MLP、完整层、模型权重、优化器或梯度检查点。

| 序列长度 | 前向加反向阶段的 MLX 分配峰值 |
| --- | --- |
| 16 | 约 246 MiB |
| 64 | 约 703 MiB |
| 128 | 约 1221 MiB（1.19 GiB） |

各组梯度有限且非零；kernel 与 ops 前向最大绝对差在本次样本中不超过约 3.82e-6。单一合成输入族不足以证明全部数值正确或稳定。

这是当前实现训练内存风险的直接证据。不能把单算子峰值机械乘以 24 当作完整训练峰值，也不能将单算子执行时间当作整模型训练速度。完整图的生命周期、冻结范围和检查点会改变结果；必须实际验证。

## 5. 已定位的执行与前沿优化限制

### 混合缓存管理

缓存包含 KV 和递推数组状态两类。复制、前缀复用、结束回收、序列回退都要同时保持两类状态一致。已安装 `make_prompt_cache` 优先调用模型自己的 `make_cache`，因此传通用 `max_kv_size` 并不证明模型真的使用了旋转缓存。KV 量化入口也只转换支持对应方法的缓存，不能视为递推状态同时量化。

### 通用推测解码不能直接启用

MLX LM 0.32.2 的通用 `speculative_generate_step` 检查缓存是否可裁剪；Qwen3.5 线性层使用的 `ArraysCache` 在该版本不具备该能力，会触发入口拒绝。递推状态不能只通过裁短 K/V 回到较早 token。

这是当前通用入口的具体限制，不代表所有 Qwen3.5 推测解码方法都不可行。实现状态快照/重算或使用专项方法，均需额外设计与数值验证，不能承诺为即开即用的首个优化实验。

### 模型有 MTP 不等于当前路径使用 MTP

已安装语言模型权重整理会过滤 `mtp.` 权重；普通生成路径不能据模型卡的 MTP 描述就认定已启用多 token 预测。专项 MTP 转换包和执行路径需要单独核验，不默认纳入最小闭环。

### 平台优化经验的迁移边界

可以学习数据流、状态管理、精度、内存带宽、profiling 与实验方法。CUDA 专用 kernel、NVIDIA 低精度指令等无法在这台 Mac 上直接实测；不能把 Metal 上的收益数值外推。计时须触发实际执行并同步，区分编译、预热和稳定执行。

相关上游源码：[生成入口](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/generate.py)、[缓存](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/cache.py)、[递推](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/gated_delta.py)。本文结论以本地锁定版本检查为准，上游主分支可能改变。

## 6. 后训练与在线强化学习堵点

SFT/LoRA 首先核验：

- 模板、thinking 开关、结束 token、训练标签和 response-only mask；推理模板与训练配置一致。
- LoRA 覆盖常规 Attention 与线性层的实际模块，不机械套用另一模型的 q/v 名称；核对冻结参数、实际梯度与更新。
- 起步禁用跨样本 packing，验证 padding、长度和样本边界。仅调整 Attention mask 不等于清除了递推状态，不可假设 EOS 自动实现状态重置。
- 验证训练/推理模式切换和数值差异，训练产物绑定模型与量化来源，先使用独立 adapter，不以融合/重新量化结果掩盖差异。
- 可恢复训练需要优化器、进度、随机与数据状态；仅保存 adapter 不能当作精确断点恢复。

在线强化学习还需验证生成、动作 log-prob、旧策略/参考策略（如算法要求）、奖励、优势、梯度与权重更新的完整一致性。不能直接照搬依赖 PyTorch/CUDA 的训练命令，也不应默认自行重写整套算法。

已发现可参考的 MLX 项目，例如 [mlxrl](https://github.com/inductiveML/mlxrl) 与 [mlx-tune](https://github.com/ARahim3/mlx-tune)。它们的支持声明不是本机验证。mlxrl 报告过 Qwen3.5-9B、group=2、seq≈609、逐层 checkpoint 的约 25.9 GB 峰值；该作者测量超过本机总内存的量级，但并非本机同配置复现，也不是所有实现的下界。这足以将 9B 中等长度 GRPO 视为高风险，而非因 4-bit 权重约几 GB 就判定可行。

优先采用可验证奖励、有限生成长度、少量组内回答、逐个或 microbatch 重算梯度；若需改变算法的 KL/参考策略等设定，需明确记录，不为省内存静默修改目标。长思考截断、奖励全相同、生成与训练 log-prob 不一致均可能造成实验“能跑但没有有效学习”。

## 7. 可解释性持续观察

可从 token 概率、层输出、残差变化、线性状态摘要和训练前后样例对照开始；不要求解释方法原理或优化。Qwen3.5 的混合结构意味着某些传统 Attention 可视化或依赖特定框架的工具只能覆盖部分层或需要适配。

不要为拿到完整 Attention 矩阵就让正常推理路径退回昂贵实现，再把该测量当作正常性能。优先选层、选 token、选样例，单独执行观察；工具/方法改变时保留版本，区分现象与机制解释。大词表、全层激活与长上下文同时导出也可能成为内存和磁盘瓶颈。

## 8. 4B 到 9B：复用与重做边界

两者布局、缓存维度和词表规模接近，模型执行外层、数据处理、实验记录与观察思路有较多复用价值；但升级并非原权重继续训练。

- 4B hidden size=2560、MLP intermediate=9216；9B 为 4096、12288。4B 共享输入/输出 embedding，9B 不共享。权重和常用 LoRA 张量形状不同，adapter/优化器状态不直接迁移；即使个别形状相同也不构成有效迁移依据。
- 即便缓存形状相同，内容来自不同权重，不能跨模型复用。
- 4B 的 tokenized 数据也要经过最终 tokenizer/template revision 校验，不能仅凭相同词表大小认定等价。
- 9B 必须重新验证加载、生成、缓存正确性、LoRA、重载和在线强化学习，重建基线，再开始正式优化。
- 不假定速度按参数量成比例，或 9B 在目标任务一定更好；M4 带宽、算子效率、序列长度和量化实现共同影响结果。

选型阶段曾比较以下两种策略；现已采用第 1 条并将 9B 迁移明确为二期，第 2 条不再作为当前执行计划：

1. 4B 为固定主目标，9B 仅作后续迁移验证；更容易让一期推理与训练投入相当。
2. 4B 仅作最小探测，正式优化前就验证 9B 的训练/RL边界，全部通过后固定 9B。不要先做完一整套 4B 优化，再默认无成本升级。

如 9B 只适合推理、不适合约定训练，不自动采用“9B 推理 + 4B 训练”作为固定单模型方案；需要单独修改目标，或继续以 4B 为主。

## 9. 更大规模、磁盘和时间

下一档稠密模型 27B：仅按名义语言参数估算，BF16 权重约 54 GB，理想 4-bit 约 13.5 GB，尚未计量化元数据、未量化层及执行开销。可能存在极受限的量化短推理配置，但不宜承诺作为本机推理与后训练兼顾的主目标；降低到更低位宽也会增加新的质量和执行问题。

本次卷剩余约 68 GiB（动态快照）。同时保留官方完整 4B/9B BF16 权重、两个量化包、转换临时副本、融合模型和检查点，会快速消耗空间。先只保留一个候选包，记录原始与转换来源，优先保存 adapter；不为本项目自动删除其他数据。升级前核对实际新增文件和转换峰值。

常规小时级、少数约 8 小时是实验预算，不是可行性保证。先测短完整步骤，再估计：

`总时间 ≈ 初始化 + 更新次数 × (采样 + 必要概率重算 + 反向更新) + 评估 + 保存`

生成长度、GRPO 组大小和检查点重算会显著改变成本。本轮算子测试含编译等开销，不能用于承诺 tokens/s 或整个训练时间。

## 10. 固定主目标前的通过条件

1. 范围明确允许仅使用 Qwen3.5 的语言部分，保持多模态实践不在项目内。
2. 固定一个候选 revision 和可信转换来源，完整加载与模板生成通过。
3. Full attention 缓存、递推状态和分段生成有对照；缓存快照、重载与生命周期正确。
4. 小规模 LoRA 实际更新、逐层检查点、有限序列训练及新进程重载通过，记录内存和时间。
5. 在最终主模型上至少跑通一次受控在线强化学习更新，验证策略梯度而非仅观察 loss。
6. 至少一种观察方法可复现；至少一个不依赖当前未支持特性的优化方向可执行。
7. 完成完整步骤的预算，确认小时级与少数 8 小时实验能够承载计划；若失败，明确调整模型或需求。

最大风险排序：递推反向内存与训练效率 → 在线强化学习完整成本/正确性 → 混合缓存对前沿优化的限制 → 量化与重载链路 → 观察工具适配。仅前向推理的资源预算不是当前最大障碍。

## 11. 补充方案：4B 完整学习后开展 9B 迁移

用户补充约束：内存不足可以作为硬件适配问题研究；常规训练不能长期妨碍本机其他工作，磁盘不能用满。现已确认将原一期拆为 4B 完整学习和 9B 迁移两期；具体 9B 实验规模与资源数值仍需短验证和边界确认。

### 阶段目标与验收

- 阶段 A 固定 4B：完成一期主线、基线、实验与方法记录。它是正式学习对象，不因将来迁移而被视作一次性试跑。
- 阶段 B 固定 9B：先建立新的行为与资源基线，再验证已学方法的迁移。作为二期，不纳入一期完成条件；原扩展专题顺延为第三阶段。
- 迁移范围建议包括加载与生成、混合缓存正确性、一次代表性 LoRA 及重载、有限的受控 RL 更新、一个优化方法和一组可解释性观察。复用学习方法，不要求重做每项 4B 实验或重新产出整套原理材料。
- 若某项不满足资源、时间或共存要求，保留诊断与适配证据，显式标记该项未通过。完成迁移边界分析可以是有效学习成果，但不能把它写成 9B 完整训练能力已经实现。
- 各阶段只维护一个活动目标，阶段内不持续兼容和自动切换不同模型。4B 产物可追踪和复现，代码可有针对性局部修改，不预先设计通用模型适配系统。

### 主要代价

1. 总项目增加一个迁移里程碑；完整学习 4B 后不等于对 9B 的资源问题已经有答案。
2. 数据、测量和模块边界通常可复用；adapter、优化器状态、缓存与调优结果不能直接搬过去，需要新训练与基线。
3. 4B 的最佳配置未必适合 9B。缩短序列、减少训练层、降低 rank、量化或重算会改变不同的条件，报告必须同时保留效果与成本。
4. 先测各模型自己的基线到优化版本，再比较相同负载下的模型规模差异；避免把换模型和换优化方法同时进行造成错误归因。

### 资源适配与共存的实验要求

- 为每次实验先估算峰值，逐级验证长度、batch 与层覆盖，不通过故意挤满整机内存来复现 OOM。
- 量化、microbatch 与检查点等可作为适配候选。它们的代价不同；节省内存后若耗时或系统干扰不合格，不能仅因不再 OOM 就判定适配成功。
- 区分“日常共存”与“空闲重负载”两种运行配置，记录系统应用负载。共存实验评价机器响应、内存压力、交换增长和实验进度；空闲实验仍遵守磁盘与总内存边界。
- 限制显存/内存分配与释放缓存并不等于限制 GPU/CPU 使用率，也不能单独保证前台交互流畅；必须在用户实际应用负载下短测。
- 长实验优先在完整训练步边界保存和退出，记录恢复所需状态；不能把仅保存 adapter 当作精确训练恢复，也不把强制终止正在执行的算子视为无损暂停。
- 具体共存条件、项目磁盘上限、系统最小剩余空间和中止阈值在正式长运行前确定。初始建议可用独立预算讨论，但未确认前不宣称已具备自动资源保护。

### 磁盘产物管理

- 分别列出下载、转换、融合和保存时的临时峰值与长期保留量，记录文件来源与 revision。
- 每阶段仅维护一个活动模型目录，避免把同一权重重复复制到缓存、工作目录和每个检查点。
- 平时保存 adapter、配置、评估与观察摘要；完整权重、融合产物和大张量只为明确实验生成。
- 迁移前保留 4B 的复现记录与必要产物；若需移除可重新获取的权重，先核对恢复来源与本地修改，不自动删除用户其他数据。
- 两套查询的量化权重文件合计约 9 GB，并非磁盘主风险的全部；原始 BF16、多份转换产物和不断增长的检查点才容易使预算失控。

### 建议的最终判断方式

4B 完成后，再决定 9B 是完整替代目标、受限迁移实验，还是只完成资源边界诊断。选择应由实测决定，不预先保证现有硬件能通过所有项目；与日常工作无法共存的实验只进入约定的空闲窗口，不能反过来迫使用户长期让出机器。
