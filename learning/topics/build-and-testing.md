# 构建、测试与模块组织

## CMake、CTest、GoogleTest 的分工

| 工具 | 负责什么 | 不替代什么 |
| --- | --- | --- |
| CMake | 描述目标、源文件、编译选项与依赖，生成构建系统 | 不替代编译器或测试断言 |
| CTest | 按注册信息运行测试进程、筛选测试、收集退出结果 | 不负责在 C++ 中比较数值或表达断言 |
| GoogleTest | 在 C++ 程序中组织测试用例、断言、fixture 和诊断信息 | 不负责整个仓库的构建和多语言检查调度 |

GoogleTest 可以独立使用，不依赖 CTest。二者也可以配合：CMake 构建 GoogleTest 测试程序，CTest 启动它。测试规模小时，普通 C++ 可执行程序通过退出码报告结果也足够；断言和用例组织变复杂时，再引入测试框架。

`include(CTest)` 启用相关基础设施，并提供 `BUILD_TESTING` 开关；`add_test` 注册要运行的命令。构建测试程序与执行测试是两步，运行 CTest 前通常需要先构建。

## 测试名称为什么写成正则

```sh
ctest --test-dir runs/d0/build -R '^gpu\.smoke$' -V
```

这条命令假定已经按 [构建指南](../../docs/build.md) 创建对应构建目录。

- `--test-dir` 选择构建目录中的测试注册信息。
- `-R` 按正则筛选测试名称。
- `^` 表示开头，`$` 表示结尾，`\.` 表示字面量点。
- 单引号将表达式原样传给命令，`-V` 显示详细输出。

测试名本身只是 `gpu.smoke`。上述表达式精确匹配完整名称；写 `-R gpu` 也可以，但会匹配所有名称中包含 `gpu` 的测试。复杂的是精确匹配表达式，不是测试名。

## 源文件、目录和构建目标是三个概念

```cmake
add_library(lab_compute STATIC mlx_runtime.cpp)
add_subdirectory(compute)
```

第一行示意如何用明确的源文件构建静态库；第二行示意进入子目录处理它自己的 `CMakeLists.txt`。它们是不同用途，不是必须在同一文件中这样连写。

- 目录用于组织文件。
- 目标是编译与链接的单位，一个目录可以定义多个目标。
- 源文件列表说明哪些文件属于目标，不能把目录直接当成源文件列表。

模块维护自己的目标和依赖，根目录负责项目配置与模块入口，可以避免根构建文件不断膨胀。源文件显式列出，也能清楚审查哪些文件进入正式程序；不必扫描整个 `src/`，否则可能把 CLI 的 `main`、无关模块等混在一起。

`cmake/` 按职责保存构建集成；用于定位 SDK 的 Python 文件也可以放在那里。目录职责不由文件后缀决定。仓库检查属于验证体系，放在测试目录更清楚。

## 测试先写，还是边开发边写

TDD 的关键是围绕一项可观察行为形成“小步失败—实现—通过—重构”的反馈，不是提前写出所有未来测试，再让它们长期跳过。

- 契约明确的行为，如 JSON 格式、错误退出和额度拒绝，适合先写测试。
- 数值功能先确定可信参考和容差，再实现并对照；文本看起来合理不等于计算正确。
- 对未知框架接口可以先做有限探索，弄清语义后再提炼正式接口和回归检查。
- 性能优化先有正确性和性能基线，再比较修改收益。

固定矩阵与预期值是测试数据，不属于产品初始化接口。产品负责实际能力，测试调用产品验证该能力，避免为了检查方便把样例执行塞进正式路径。

## 复习问题

- GoogleTest 的断言失败后，CTest 如何知道测试失败？为什么二者不互相替代？
- `-R gpu.smoke` 与 `-R '^gpu\.smoke$'` 的匹配范围有什么差别？
- 为什么不能把整个 `src` 目录直接交给 `add_library`？
- 一个暂时不知道预期输出的数值接口，应该如何建立测试依据？
