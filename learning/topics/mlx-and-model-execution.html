MLX、Metal 与模型执行

MLX 不是 Python 实现的计算核心

MLX 的计算核心使用 C++，Apple GPU 执行通过 Metal 后端实现。Python 绑定和 C++ 接口提供不同的调用入口：

Python 程序 → Python 绑定 ─┐
                         ├→ MLX 核心 → CPU / Metal GPU
C++ 程序 → C++ 接口 ─────┘

C++ 包含 MLX 头文件并链接原生动态库，可以直接使用张量、算子和自动微分，不必先调用 Python。通过 Python 安装包获取头文件与库，是依赖分发方式；文件放在 .venv 里不改变其实现语言，也不意味着原生程序需要 Python 解释器。

SDK 是开发所需文件的集合，主要包括头文件、动态库、Metal 内核库和 CMake 配置。接口查阅应使用 C++ 文档及所用版本的头文件，不能假定 Python 签名与 C++ 一致。

Metal 为什么会出现在项目中

Metal 是 Apple 平台访问 GPU 的图形与计算 API；MSL 是编写其 GPU 内核的语言。C++ 主语言与 Metal 内核不是相互替代关系：C++ 组织程序和张量计算，内核处理适合 GPU 并行执行的局部计算。

大部分操作可以直接使用 MLX 的现成算子。已有接口无法满足明确的数值契约，或性能分析发现值得处理的局部瓶颈时，再评估局部扩展；优先复用经过验证的计算组件。扩展会增加正确性、梯度和维护成本，前向通过也不自动说明反向已经可用。

MLX 已经提供张量后端抽象，项目无需逐项重封装。薄的计算扩展层集中管理自定义内核、调用参数和版本相关接口；上层表达张量语义，不散布设备、pipeline、线程组等细节。这个边界有利于阅读和修改，但不保证未来框架升级只需改一个文件。

MLX 与 MLX-LM 的区别

MLX 提供计算基础；MLX-LM 基于它提供模型结构、生成、加载与微调等上层功能，主要使用 Python。能使用 MLX 的 C++ 接口，不代表能够直接复用 MLX-LM 的 Python 模型和训练代码。

从学习目标出发，可以直接复用张量运算与自动微分，同时实现固定模型所需的前向、缓存、生成和训练流程。这样能观察 token、状态、梯度与参数更新，不必重写完整通用框架。正式复用边界见 实现约定。

代价是权重映射、布局、状态更新和梯度链路需要逐段对照。应先对齐固定输入下的中间张量与 logits，再验证缓存解码，随后验证 loss、梯度和一次参数更新，最后才优化。

三个容易混淆的判断：

  • 生成文本合理，不等于实现正确。
  • 推理正确，不等于反向传播正确。
  • 量化权重能推理，不等于相同链路自然支持 LoRA 训练。

分词、JSON 和文件格式等支撑工作则优先使用成熟组件，避免为了特色消耗主要学习时间。学习深度取决于能否解释、观察和诊断，而非自行实现的代码量。

为什么仍有 Python 环境和锁文件

pyproject.toml 声明辅助环境与依赖要求；uv.lock 保存解析出的精确依赖版本、来源与包文件哈希；.venv/ 是安装后的本地环境。

锁文件便于重建一致的依赖集合，但不固定编译器、操作系统、解释器二进制或数值执行的全部条件。Python 版本范围较窄可以表示项目只验证了这一工具环境，不代表 MLX 本身只支持这一版本。选择升级时应验证，而不是把已验证范围误认为底层能力限制。

  • 在什么观察结果下，才值得考虑自定义 Metal 内核？
  • 直接使用 MLX-LM 与参考它实现固定模型流程，各省去了什么、又学到了什么？
