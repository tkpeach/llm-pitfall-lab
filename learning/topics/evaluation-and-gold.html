为什么可以用 gold 评估 LLM，又为什么不能只看严格匹配

本笔记来自对 evaluate_record 的提问及 2026-10-26 的调研。当前选择保留严格基线、优先扩大可信评估数据；诊断指标等其余建议作为后续参考，不要求立即实现。当前正式规则见 任务契约。

Gold 不是要求模型背答案

Gold 是给定输入及任务规则下的参考标注。模型看到输入和输出要求，不看到测试答案；评估器在生成结束后比较。能否可靠评分，取决于输入是否足以确定答案、标注是否正确、测试是否独立，以及“什么算相等”是否符合任务。

订单原文 → LLM 抽取与归一化 → 完整输出文本
                                  ↓
                       JSON 校验 → 字段比较 ← gold
                                  ↓
                          任务分数与错误诊断

当前 C++ 代码实现的是后半段正式评估，不只是 TDD 测试，也没有实现基于原文的抽取。测试调用评估器确认尺子可靠；目标模型接入后才测量模型。六条契约样例不是效果测试集。

当前 == 比较的是 JSON 解码后的字段值：键顺序、对象外空白和等价 Unicode 转义不影响结果；字符串里的空格、同义表达、类型差异仍影响结果。没有自动语义匹配。“比较规范值”并不意味着评估器已经把任意表达归一化。

代表性工作如何做

下面是相关产品与论文的实例，不代表全行业只有一种标准；文档类基准只借鉴评价方法，不引入本项目范围外的 PDF/OCR 或多模态流程。

工作 使用的方法 对本项目的启发
Google Document AI 预测实体与测试标注比较，报告 precision/recall/F1；按类型及值匹配，可选空白、大小写等匹配放宽规则 gold 对照是实际产品采用的方法，但匹配政策必须明确
LLMStructBench，2026 将自然语言到 JSON 的结构、值错误和文档级正确性分开观察，采用多种互补指标；包含其自行定义的带部分分数的 F1 指标 JSON 能解析与内容正确是两个问题，不能只比较一个总分；论文中的 F1 也未必是标准定义
ExtractBench，2026 根据字段分别选择精确、模糊、数值容差或语义比较；区分遗漏、幻觉与错误值，数组需先对齐 比较器应服从字段语义，不能为所有字段统一套相似度
JSONSchemaBench 将约束解码的效率、schema 覆盖与输出质量分别评估 格式约束与内容质量要独立测量；引入约束解码时不能只宣布 JSON 合法率提高
MT-Bench / LLM-as-a-Judge 用强模型评判开放回答，并分析位置、冗长和自我偏好等偏差 语义裁判有用途，但不是无误差的 gold 替代品，需要人工校准

相等规则应该由字段决定

对于本项目，以下是基于任务语义的建议，而非照搬上述基准的默认设置：

  • 订单号、数量、币种以及按最小单位保存的金额，通常应精确匹配。订单号只差一个字符或金额只差一位都可能是实质错误，不能因为文本相似就给满分；本任务没有默认金额容差。
  • 日期若要求 YYYY-MM-DD，2026/11/02 可能表达同一日期，但仍违反输出契约。可在独立诊断中分析这一差异，不应悄悄修改严格成绩。
  • 商品名称当前要求原文名称，因此严格匹配有依据。但“名称边界在哪里”仍需标注规则说明；若允许简称或别名，应提前定义可接受答案集合或规范映射，不能看到模型答案后临时认定等价。
  • 开放描述更适合人工 rubric、语义裁判或显式的多参考答案。编辑距离、token 重叠或 embedding 相似度可作诊断，不保证事实相同，尤其不适合放宽编号和金额。

标准化不是不能做，而是必须声明它属于任务输出要求、独立评估政策还是产品后处理。若比较后处理方案，应分别报告原始输出和处理后结果，并记录额外成本，不覆盖严格原始基线。

当前方法能预期测出什么

严格评分便宜、确定、可重复，适合观察提示、SFT、精度和优化变化对固定任务的影响。但无法据此预估 Qwen3.5-4B 的具体准确率；当前没有目标模型实测，其他论文的模型或任务分数不能移植过来。

整条正确率会比字段正确率低。例如仅为说明指标，假设六个字段独立且各有 95% 正确率，则整条约为 0.95^6 ≈ 73.5%；实际字段并不独立，不能用此式预测模型表现。

当前六条契约样例中，全 null 输出能得到 13/36 字段匹配，却是 0/23 非空字段匹配。这说明总体字段分数可能被“正确缺失”抬高。它是评分机制的例子，不是模型实验。

当前还将非法记录全部字段计错，这适合衡量端到端是否可用，却会使一个类型错误掩盖其他字段的正确内容。可以增加明确标为诊断的分项观察，但严格主分数仍应保留所有失败，不从分母删除。只对合法答案算出的内容准确率属于条件指标，不能替代端到端指标。

值得进一步完善的评估组合

  1. 保留严格基线。 继续观察格式阶段、逐字段、整条以及 gold 空/非空指标；这些已实现。
  2. 增加错误分类。 将漏提取、原文无值却补出值、错值及类型错误分开；需要时增加 precision/recall/F1。必须先定义计数政策：一个错误的非空值通常同时涉及错误预测和漏掉正确值，不能直接把当前准确率改名为 F1。
  3. 完善数据设计。 独立划分训练、开发与封存测试，按订单场景/改写家族分组；覆盖缺失、明确更正、金额与日期转换、干扰文本和表达变化。超出 v1 的多商品、矛盾等仅在显式修订任务后纳入，不偷偷扩充验收范围。
  4. 人工检查少量代表性错误。 区分模型失败、标注错误和评分过严；规则在开发集确定，修改后版本化重建基线，不依据封存测试反复调规则。若简单样本已接近满分，再建立有真实错误空间的任务版本。
  5. 实验结论分层。 任务分数检查应用效果；logits、缓存和梯度对照检查实现正确性；时延、吞吐、内存、磁盘和恢复对照检查系统目标。三者不能互相替代。

确定性字段无需优先引入另一台大模型当裁判。自由文本或歧义判定需要时，再考虑参考原文的局部语义裁判，并对照人工样本、固定版本与 rubric、记录成本。人工或模型裁判也不能凭 gold 和预测两段文字就可靠判断原文是否支持某个事实。

用于训练的候选奖励与独立效果评估也要分开审查：能作为确定性评分，不代表奖励不会被利用。未来 RL 阶段需检查全 null、模板记忆等捷径，并保留独立评估；这里只提出风险，不变更已确认的 RL 契约。

复习问题

  • 为什么“键顺序不限”与“字段值必须严格相同”不矛盾？
  • 如果模型输出日期语义正确但格式错误，端到端指标与诊断指标应如何表达？
  • 全 null 的总体准确率为什么可能不低？precision/recall/F1 又需要先定义哪些计数规则？
  • 相同的任务分数，为什么不能证明两个缓存实现数值正确？
  • 使用语义裁判后，如何发现它把看似相近但事实不同的答案判对了？
