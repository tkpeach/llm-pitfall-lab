# 中文订单抽取任务 v1

一期选择单条中文订单描述，抽取一个商品条目。它用于检查数据、生成、SFT 与可验证奖励，不作为业务产品。先用人工可审查的合成契约样例验证流程，再构造独立训练/验证/测试集；契约样例不是效果评估集。

## 输入与输出

输入为订单原文；输出为唯一 JSON 对象，不带代码围栏、解释或其他文本，必须恰好含下列 6 个键。

| 字段 | 类型与规则 |
| --- | --- |
| order_id | 字符串或 null；仅提取明确订单号，保留原样 |
| product | 字符串或 null；原文商品名称，不扩写 |
| quantity | 正整数或 null；中文整数可归一化，不把 bool 当整数 |
| unit_price_minor | 非负整数或 null；明确单价换算为最小货币单位，39.90 元输出 3990；不从总价推导 |
| currency | CNY、USD 或 null；仅在原文明确时填写，不依据语言、地名或孤立的 $ 猜测 |
| delivery_date | YYYY-MM-DD 字符串或 null；只处理明确的绝对日期，不推断“明天”等相对日期 |

缺失字段为 null，不省略。v1 只覆盖 CNY/USD（均按两位小数）。多商品、多币种冲突、无法消解的矛盾、超过两位小数的金额先排除在训练数据之外，作为后续困难集；明确更正的样例应人工按最终值标注。有限范围必须在结果中说明。

示例输入：`订单号 A-102，订购蓝色笔记本三本，单价人民币 12.50 元，要求 2026 年 11 月 2 日送达。`

示例输出：

```json
{"order_id":"A-102","product":"蓝色笔记本","quantity":3,"unit_price_minor":1250,"currency":"CNY","delivery_date":"2026-11-02"}
```

## 评估契约

- 严格解析：拒绝重复键、非有限数、额外文字与额外键。JSON 键顺序和空白不影响结果。
- 先报格式/类型/日期有效率，再报整条严格准确率和各字段准确率；非法输出整条及全部字段均计错，不能从分母移除。
- 将 gold 非 null 与 gold 为 null 的字段分别统计，暴露“全部输出 null”捷径。
- 归一化规则定义在数据标注阶段，评估器不二次修复模型答案，不用宽松解析掩盖错误。
- 受控 RL 的候选内容奖励为字段准确率，非法格式为 0；必须同时记录整条准确率、非空与缺失字段指标，不能只优化 JSON 格式。具体奖励与算法在 RL 阶段单独验证。

### 严格校验与数值边界

评估器依次检查 JSON 解析、恰好六键的对象结构、字段类型/取值范围、真实公历日期，报告各阶段通过数及比率。阶段指标累积计算，分母均为全部 gold 样例；前一阶段失败时后续阶段不通过。日期允许年份 0001–9999；null 日期通过日期检查，不要求额外补全。

当前原生评估使用有符号 64 位整数：数量为 1–9223372036854775807，单价最小单位为 0–9223372036854775807。布尔值、数字字符串、小数或指数写法（如 `1.0`、`1e0`）不作为整数接收；不执行字符串裁剪、大小写转换或数值修复。JSON 转义解码和键顺序差异不影响值比较。

### 离线评估输入与报告

gold 文件沿用 `fixtures/task_contract.json` 的数组格式，每条恰好包含唯一非空字符串 `id`、字符串 `input` 和规范 `gold` 对象。该文件必须非空；评估器检查标注结构与类型，不自动判断标注是否符合原文语义。

预测文件是 JSON 数组，每条恰好包含 `id` 和字符串 `output`。`output` 保存模型的完整原始文本，使围栏、解释、重复键等错误可以被检测，而不是事先解析或修复。例如：

```json
[{"id":"no-order-data","output":"{\"order_id\":null,\"product\":null,\"quantity\":null,\"unit_price_minor\":null,\"currency\":null,\"delivery_date\":null}"}]
```

按 ID 匹配，顺序不限。gold 中缺少预测的样例仍保留在全部分母中，按非法输出计错；未知/重复预测 ID、非法 gold、损坏的外层文件或错误字段结构属于评估输入错误，拒绝生成报告。预测原文不合法属于模型答案错误，照常计分，二者不能混淆。

报告包含各校验阶段、整条与字段准确率的 `correct/total/rate`，各字段及汇总的 gold 非空/为空分组指标，以及逐样例错误、字段正确标志和候选奖励。分母为零的分组比率为 null。候选奖励仅为合法答案的六字段准确率，不代表在线强化学习闭环已经验收。

当前命令为小批量离线评估，单个输入文件上限 16 MiB，JSON 嵌套最多 128 层；报告写至标准输出。此输入边界不替代 D2 的统一磁盘预算保护，亦不承诺大数据集流式处理。操作见 [构建与检查](build.md#离线任务评估)。

## 数据计划与学习验收

当前 `fixtures/task_contract.json` 是手写合成规则样例，可供本项目使用，不含用户私有业务数据。它仅验证任务契约、评估器与命令，不用于宣称训练效果或泛化。

当前优先扩大独立、可信的评估数据，维持已实现的严格计分。错误分类、precision/recall/F1、语义裁判等保留为 [方法参考](../learning/topics/evaluation-and-gold.md)，按后续真实需求考虑，不在本轮增加验收范围。

[评估种子集 v1](../fixtures/order-evaluation/v1/README.md) 提供 52 条原创合成候选样本，按 26 个订单/改写组隔离为 dev 与 test 候选，各 26 条。它记录来源、规则标签、逐字段证据或缺失理由、版本与哈希；独立人工复核和测试冻结尚未完成，不能称作已验收的真实业务测试集。原六条契约样例继续单独保留。

正式数据按场景/改写家族分组划分，避免同一底层订单的改写跨训练与测试。分别保存原文、规范答案、规则标签、分组 ID、来源/许可及版本；划分后不依据测试结果反复挑选训练数据。数据集规模、难度和效果目标由 4B 基线确定。

先在开发/验证数据检查任务是否存在足够的真实错误空间。若基线接近满分，修订任务版本与开发数据，不以查看封存测试集后的调题代替泛化评估；需要新测试集时独立构造并记录版本，重新建立对照。二期尽量复用冻结的评估数据，区分模型规模与训练影响。
