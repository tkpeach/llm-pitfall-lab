# 中文订单抽取任务 v1

一期选择单条中文订单描述，抽取一个商品条目。它用于检查数据、生成、SFT 与可验证奖励，不作为业务产品。先用人工可审查的合成契约样例验证流程，再构造独立训练/验证/测试集；契约样例不是效果评估集。

## 输入与输出

输入为订单原文；输出为唯一 JSON 对象，不带代码围栏、解释或其他文本，必须恰好含下列 6 个键。

| 字段 | 类型与规则 |
| --- | --- |
| order_id | 字符串或 null；仅提取明确订单号，保留原样 |
| product | 字符串或 null；原文商品名称，不扩写 |
| quantity | 正整数或 null；中文整数可归一化，不把 bool 当整数 |
| unit_price_minor | 非负整数或 null；明确单价换算为最小货币单位，39.90 元输出 3990；不从总价推导 |
| currency | CNY、USD 或 null；仅在原文明确时填写，不依据语言、地名或孤立的 $ 猜测 |
| delivery_date | YYYY-MM-DD 字符串或 null；只处理明确的绝对日期，不推断“明天”等相对日期 |

缺失字段为 null，不省略。v1 只覆盖 CNY/USD（均按两位小数）。多商品、多币种冲突、无法消解的矛盾、超过两位小数的金额先排除在训练数据之外，作为后续困难集；明确更正的样例应人工按最终值标注。有限范围必须在结果中说明。

示例输入：`订单号 A-102，订购蓝色笔记本三本，单价人民币 12.50 元，要求 2026 年 11 月 2 日送达。`

示例输出：

```json
{"order_id":"A-102","product":"蓝色笔记本","quantity":3,"unit_price_minor":1250,"currency":"CNY","delivery_date":"2026-11-02"}
```

## 评估契约

- 严格解析：拒绝重复键、非有限数、额外文字与额外键。JSON 键顺序和空白不影响结果。
- 先报格式/类型/日期有效率，再报整条严格准确率和各字段准确率；非法输出整条及全部字段均计错，不能从分母移除。
- 将 gold 非 null 与 gold 为 null 的字段分别统计，暴露“全部输出 null”捷径。
- 归一化规则定义在数据标注阶段，评估器不二次修复模型答案，不用宽松解析掩盖错误。
- 受控 RL 的候选内容奖励为字段准确率，非法格式为 0；必须同时记录整条准确率、非空与缺失字段指标，不能只优化 JSON 格式。具体奖励与算法在 RL 阶段单独验证。

## 数据计划与学习验收

当前 `fixtures/task_contract.json` 是手写合成规则样例，可供本项目使用，不含用户私有业务数据。它仅验证任务契约、评估器与命令，不用于宣称训练效果或泛化。

正式数据按场景/改写家族分组划分，避免同一底层订单的改写跨训练与测试。分别保存原文、规范答案、规则标签、分组 ID、来源/许可及版本；划分后不依据测试结果反复挑选训练数据。数据集规模、难度和效果目标由 4B 基线确定。

先在开发/验证数据检查任务是否存在足够的真实错误空间。若基线接近满分，修订任务版本与开发数据，不以查看封存测试集后的调题代替泛化评估；需要新测试集时独立构造并记录版本，重新建立对照。二期尽量复用冻结的评估数据，区分模型规模与训练影响。
