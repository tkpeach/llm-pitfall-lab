# 一期最小设计与验证关口

本文件规定一期 C++ 实现的模块边界与最小链路关口。语言、计算扩展层、SDK 和配置职责见 [实现约定](implementation.md)，当前实现状态见 [仓库现状](status.md)。

## 边界与数据流

```text
CLI → 配置加载与资源预检 → 任务数据/评估
              → 运行控制 → 模型执行/训练步骤
                         → 完整检查点 → 显式恢复
                         → 小型观察与实验报告
```

- `task`：严格输出契约与评分；不承担模型推理或修复答案。
- `data`：数据版本、划分、tokenization、模板、labels/mask 和消费进度；与模型计算及评分分离。
- `resources`：卷空闲检查与预计新增峰值预检；项目总占用留待阶段性盘点。不自动删除、不修改系统设置。
- `checkpoint`：原子提交、完整性及配置身份校验；运行状态不能静默跨配置恢复。
- `runner`：暂停请求、步边界保存与退出。暂停后由用户显式恢复；不挂起仍占内存的进程。
- `model`：固定 Qwen 加载、生成、混合状态和 LoRA 执行；观察在独立运行中采样，不替代主执行路径。不预先实现服务调度或多模型插件。
- `compute`：集中接入专用计算和 Metal 扩展，维护输入输出、状态及梯度契约；不重封装整个 MLX。
- 观察与报告在相应边界采集，绑定模型、代码与配置身份；性能采集与带详细观察的运行分开，不要求搭建通用监控平台。

小型机制与样例训练环属于 `tests/` 中的验收程序，调用正式模块验证 optimizer/RNG/数据顺序等状态，不作为正式模型后端或失败兜底。产品模块只承载实际执行需要的能力。

## 首轮关口

| 关口 | 产物与通过条件 |
| --- | --- |
| D0 正式构建与一致性入口 | CMake 明确使用 C++23，显式定位固定 MLX SDK，验证实际使用的标准库特性；建立本地检查与 CTest，检查文档导航和依赖锁；正式目标不依赖 research 的代码或运行时配置 |
| D1 任务契约 | schema、标注规则、手写样例、严格评估及错误用例 |
| D2 资源与检查点 | 加载和校验统一资源配置；轻量检查卷空间与声明峰值，项目用量未知时明确报告；检查点完整性、身份错误拒绝与原子提交 |
| D3 安全控制机制实验 | 独立进程中连续训练对比暂停/恢复；参数、optimizer、随机、数据进度对齐，退出后工作进程结束 |
| D4 目标模型短验证 | 预检后下载明确 revision 的单个执行产物，核验模板、关键张量与 logits、短生成、全序列与缓存执行的混合状态对照、资源与时间；不能将 D3 代替 D4 |
| D5 训练与恢复 | 对照目标模型 loss、可训练参数梯度和一次 LoRA 更新，验证 adapter 重载、完整检查点与新进程恢复，之后再安排长训练/RL |

每一关口同时要求正式代码通过行为验证、文档与行为一致、当前证据可追踪、docs/status.md 的能力与证据对应审查已更新。参考实验不直接计入正式关口；检查随模块就绪接入，不在 D0 要求实现 D2 的资源逻辑。一致性流程见 [维护约定](maintenance.md#代码与文档的一致性)。

D0–D5 仅覆盖正式最小链路，不等于一期全部完成。后续推理优化、独立效果评估、受控在线强化学习、可解释性和部署仍按 [学习规格](learning-spec.md) 验收。

检查点采用 JSON 控制状态、tensor 文件与校验清单，按格式版本组织；模型、adapter 和优化器张量不展开为 JSON 数组。采用新目录写完并校验后提交，读者只接受完整检查点。

## 模型与训练的数值对照

复用职责见 [实现约定](implementation.md#mlx-与-mlx-lm-的复用边界)。模型和训练模块采用分段对照，再建立正确性与性能基线，最后进行针对性优化：

1. 固定可复现的参考版本、权重、少量输入和执行配置，在对照前确定指标与容差。分词结果与模板先对齐，随机生成不能代替固定输入的数值检查。
2. 对齐关键中间张量和 logits，再对照全序列与缓存解码的输出及状态更新；同时覆盖 KV、卷积和递推状态，不能只检查生成文本是否合理。
3. 固定训练样本、labels/mask、adapter 初始值和优化器配置，对齐 loss、可训练参数梯度及一次更新，检查冻结参数未更新；再验证连续训练与新进程恢复。推理数值通过不代表训练链路通过。
4. 保存通过验证的实现与负载基线，再开展性能分析和局部优化；近似或量化变更同时复查数值和独立任务效果。

对照按资源预算选择短序列、少量样本及必要张量摘要，不要求同时驻留两份模型或保存全部激活。具体支撑组件、参考程序和算子方案在对应模块实现前核定；以上为验收要求，不表示目标模型对照已实现。

## 测试与开发节奏

以现有关口和学习规格作为验收场景清单，逐段开发；不预先编写全部未来能力的可执行测试，也不以长期 skip、空实现或固定返回值制造通过状态。

- 任务契约、资源规则和状态转换等确定性行为采用小步 TDD：明确一项契约，写测试并确认因缺少该能力而失败，完成真实实现，验证通过后再重构。
- 数值、梯度与混合缓存先确定可信参考、输入和容差，再实现与对照；不以生成文本合理或 loss 下降代替正确性。
- 未知框架接口先做有限探索；结论明确后提炼正式接口和回归测试，不直接将探索样例变成产品 API。
- 性能优化先保存正确性及性能基线，再测修改效果；性能波动与正确性失败分别分析，不设置未经实测的绝对速度门槛。
- 缺陷修复先保留可复现失败，再修复与回归。重构保持已验收行为及错误路径，显式记录必要的接口变化。

固定样例、参考值和断言归测试，测试调用正式实现；正式运行不调用测试。测试优先验证可观察行为和计算契约，不绑定私有类结构。未开发、已实现未验证、已验收的能力分别记录；已激活范围的测试必须执行，不能静默跳过。

## 控制与正确性

- 正常运行是唯一主路径；`resume` 必须存在有效状态，否则报错。小实验、真实模型与结果明确区分。
- SFT 的安全边界是完整 optimizer 更新，RL 按完整迭代或明确定义的可恢复子边界处理；评估按样例或小批次保存。未提交工作可重做，不重复已提交更新；梯度累积/RL 必须保存其必要状态，不能沿用不完整快照。
- 暂停请求可以来自控制命令或中断信号；请求仅设置标志，工作步骤结束后保存并退出。记录请求到退出延迟，不能承诺正在执行的 GPU kernel 即刻停止。
- 同一运行目录只允许一个 worker。保存前估算新旧状态与临时文件的峰值；原子保存保留最近有效状态，不以半写文件冒充有效状态。
- 完整恢复对照优先于额外测试数量；资源与文件格式错误需明确失败。不能因为单次 loss 下降而宣布模型能力提升。

资源预检不是系统磁盘配额。其他应用可能并发写入，库可能有未估算缓冲；大文件操作必须列清单、留余量、分段复核。系统空间不足且没有保存余量时应在开始前拒绝，不等到临界才写大检查点。

## 当前不实现

一期不实现生产服务、GUI、分布式训练、自动后台调度、通用模型适配及第三阶段专题。MoE 真实推理观察和后训练统一在第三阶段开展。
