# 文档与验收维护

新增、移动或删除正式文档时同步 [总入口索引](README.md)。目录职责变化时更新 [文档总入口](README.md)，实施状态变化时更新 [仓库现状](status.md)；具体规则只在所属专题文档维护，根 README 保留概览，AGENTS.md 保留长期协作约束。

## 代码与文档的一致性

文档定义要求，配置定义运行参数，代码实现行为，验证结果提供证据。发生冲突时先定位原因：修正偏离要求的实现，或依据已确认的变更更新规范；不能改写文档掩盖错误，也不能把设计标成已实现。

每次变更的完成条件：

1. 明确受影响的规范、配置、接口、使用命令和证据；只修改相关内容。
2. 完成实现及相应验证，同步受影响文档和示例；无需修改文档时说明理由。
3. 提交前审查完整差异，代码与对应文档尽量在同一提交交付；涉及能力、验证或下一步时更新 status.md，涉及导航或目录职责时更新 docs/README.md。

文档同步按影响和粒度判断，不意味着每次修改都新增说明。正式文档保留模块级职责、重要功能、操作入口和重要约束；局部函数实现、内部调用顺序和小幅重构由源码注释与测试承载。只有改变上述职责、行为、限制或验收结论时，才更新相应规范或现状；status.md 也不逐函数维护清单。

开发顺序遵循 [测试与开发节奏](design.md#测试与开发节奏)，每次只激活当前要实现的行为。

检查随正式模块就绪接入统一本地入口和 CTest：

| 接入时点 | 检查内容 |
| --- | --- |
| D0 | 文档链接和索引、依赖锁、SDK 与实际 C++ 标准；正式目标不依赖研究目录 |
| D1–D2 | 任务样例与评估器契约、资源配置校验、项目软预算提醒、卷空间安全线和检查点失败行为 |
| D3 | 退出和新进程恢复正确性；CLI 就绪后验证文档中的关键命令 |
| D4–D5 及后续实验 | 目标模型身份、数值与任务效果、资源和时间结论与实际证据一致 |

参数表可由 TOML、CMake 或依赖清单生成/校验；不依靠对任意自然语言的脆弱匹配。静态扫描只辅助检查，行为承诺仍需执行验证。纯文档调整检查链接、导航和内容，不因此重跑完整模型。

## 现状与证据的对应审查

- `status.md` 维护当前实现、真实调用关系、关键入口、已知限制及下一步完成条件；不写开发流水账，不复制完整规范或命令手册。
- 每项已验证能力对应 `evidence/current.json` 中稳定的检查名称或条目；现状审查其代码与环境身份是否匹配、输入及指标是否覆盖该能力、结果是否足够，明确哪些结论不能推出。失败、未实现、未验证和待复验分别陈述；证据不充分时收窄状态声明，不放宽验收要求。
- 快照记录验证时间、代码版本及工作区修改、相关源码清单与哈希、工具链、适用模型/配置、命令、输入与容差、结果和限制。检查源码身份时同时核对新增和删除文件，不能只比对已有条目。文档与快照本身不纳入源码哈希，避免自引用；文档检查单独记录验证范围。
- 代码、配置、依赖、环境或验收要求变化后，按影响重新验证；尚未复验则在现状和对应快照条目标记待复验，保留实际验证时间。未受影响条目可保留原始验证身份及理由，不伪造同一时间全量重跑。
- 快照只维护当前状态，不按阶段或普通重构追加文件；已提交历史交给 Git，未提交的临时调试记录无需永久保存。有学习价值的结果整理到 `learning/` 后再清理旧摘要。大产物仍存 `runs/`，当前结论的必要小型摘要不能只依赖可清理日志。
- 更新时双向核对：状态声明均有足够证据或明确缺口，证据条目均有用途和适用范围。此项目前为人工审查；现有 `project.docs` 只校验正式文档链接、锚点和索引，不能自动证明状态与证据语义一致或学习内容正确。

## 学习记录维护

学习笔记及 pitfall 的收录、组织与复现要求统一见 [学习记录约定](../learning/README.md)，不在本文件重复维护。仅在有值得复习的用户学习内容时更新学习记录，无须每次提交都同时修改现状、快照和笔记。
