# 受控写入与检查点

本页定义轻量检查点写入流程与容器。资源规则见 [资源规则](resource-policy.md)，当前验收范围见 [仓库现状](status.md)。D3 验证训练状态和退出恢复，D5 才验证目标模型；容器核验通过不等于完整训练可恢复。

## 写入生命周期

```text
阶段性卷空间预检 → 暂存目录 / 写入文件
                 → 文件同步 / 清单回读校验
                 → 不覆盖旧版本的原子发布
```

保存开始前只读取卷可用空间，并用请求中的 `peak_bytes` 做一次轻量检查；项目目录总占用当前不测量，报告会明确标记未知。没有跨进程独占租约，也不在每个文件块上反复做资源检查；并发写入可能竞争空间，实际写入失败仍会返回错误。

文件在项目内暂存并校验后，以同卷不覆盖重命名发布。路径逐层相对目录描述符解析，不沿目录符号链接写出项目。会话仅记录自己新建的暂存目录，以便普通失败时清理，不删除已有检查点或用户文件。该流程不提供磁盘硬配额，也不阻止外部进程写盘。

## 容器格式与身份

已发布版本位于 `runs/checkpoints/NAME/`：

```text
control.json     # format_version、identity、state（JSON 对象）
manifest.json    # format_version、identity、各文件字节数与 SHA-256
adapter.bin      # 示例文件名；实际张量由生产方序列化
optimizer.bin    # 按实际任务提供，格式不由 D2 容器解释
```

格式版本当前为 `1`。清单包括 `control.json` 与 1–128 个独立文件，文件名限制为安全的单层名称；不接受额外文件、重复文件、路径穿越、符号链接或不存在的文件。元数据上限 1 MiB、嵌套上限 128 层，重复 JSON 键拒绝。恢复核验逐文件检查大小和 SHA-256，控制文件与清单中的身份均须与调用者提供的预期身份完全一致。

身份包含四个非空字符串：`model`、`data`、`template`、`configuration`。生产方应填入固定模型身份、数据版本及模板/运行配置的可追踪版本或摘要，预期身份来自当前可信运行上下文，而非从待恢复文件自我抄录。D2 只验证这些身份一致，不能替生产方证明它们与真实环境相符。SHA-256 检查完整性，不提供对恶意重写整份清单的真实性认证。

控制状态是小型 JSON 对象，张量不展开成 JSON 数组。哪些参数、优化器、RNG、调度器和数据进度必须保存，由 D3/D5 的运行链路定义并以连续/恢复对照验证。源张量文件须先由生产方生成并保持稳定，且位于项目或明确登记的外部归属目录；不读取研究归档产物。容器不检查 `.bin`/`.safetensors` 的内部语义，尚未接入 MLX 张量序列化。

## 保存与核验命令

按 [构建指南](build.md) 构建后，保存请求的结构如下；源文件路径须为实际存在的绝对路径：

```json
{
  "name": "step-0001",
  "identity": {
    "model": "固定模型身份",
    "data": "数据版本",
    "template": "模板摘要",
    "configuration": "运行配置摘要"
  },
  "control": {"step": 1},
  "files": [{"name": "adapter.bin", "source": "/absolute/project/runs/adapter.bin"}],
  "peak_bytes": 4194304
}
```

这只是容器请求示例，不是完整训练检查点。`peak_bytes` 是本次操作的额外峰值估算，应包括暂存副本、控制/清单、目录和发布元数据。预检只用该值核对卷空闲，不自动核算项目内现有文件或检查点。示例 4 MiB 仅用于小型材料，不能直接用作真实模型预算。

```sh
./runs/d0/build/pitfall-lab checkpoint-save \
  --root "$PWD" --config configs/resources.toml --request request.json

./runs/d0/build/pitfall-lab checkpoint-verify \
  --root "$PWD" --name step-0001 --identity expected-identity.json
```

`expected-identity.json` 包含上述四个身份字段。命令成功在 stdout 输出身份、控制状态与清单，失败在 stderr 报错并退出 `1`，用法错误退出 `2`；不会加载模型或自动开始训练。`checkpoint-verify` 是只读核验，不是 `resume` 命令。当前实测使用的目录和小型示例报告见状态与证据。

## 发布、失败与保留

每次保存先建立唯一 `.pending-*` 暂存目录，写完文件并同步后生成清单，回读验证与读取端使用同一逻辑；随后执行同卷 `RENAME_EXCL` 原子发布并同步目录。目标名称已存在时拒绝，不覆盖它。读取端仅接受明确命名的已发布目录，版本不对、身份不符或文件损坏时明确失败，不扫描其他版本兜底。

旧检查点属于项目总体占用；当前预检不自动统计它们。普通失败尽力清理自己的半成品；崩溃可能留下 `.pending-*`，它不能恢复，也不会在下一次操作时被悄悄删除。需要清理时由用户确认归属和保留策略。

原子重命名是可见提交点。若重命名后目录同步失败，操作会明确报告“已可见但同步失败”；此时须核验该版本，不能假定没有提交并覆盖重试。测试覆盖实际部分写入失败，不宣称已实测进程强制终止、断电、所有文件系统错误或存储硬件持久性。

## D2 验证与后续接入

- 确定性测试检查卷空间峰值预检、身份错误、已知 SHA-256、路径和格式边界。
- 检查点测试用文件大小限制触发真实部分写入失败，确认失败版本不会发布且旧版本仍可核验。
- 任务评估和只读 `resources` 保持原路径。当前受控生产写入由 `checkpoint-save` 接入；未来下载、转换和 MLX 序列化必须接入同一运行上下文，不能宣称库存在就自动保护任意命令。
- 下一步 D3 在安全更新边界组织真实训练状态，验证主动暂停、完整保存、退出资源释放及新进程继续，不以容器往返代替这些能力。
